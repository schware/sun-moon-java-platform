# 총정리 — 2026-09-17 ~ 18, 그리고 다음 주에 이어서 할 것

이 문서는 **다음 작업을 여는 사람**(아마 다음 주의 Sun&Moon과 Claude)을
위한 것입니다. ADR은 "왜 그렇게 정했나"를 남기고, 이 문서는 "지금 어디까지
왔고 다음에 무엇을 집어야 하나"를 남깁니다.

## 1. 이틀 동안 무엇이 생겼나

### POS-Server 가 중계에서 기록으로 (업무 정의서 §3 전부)

Device Server(8087)는 어제까지 아무것도 갖고 있지 않았습니다. 단말 소켓을
들고 Order·APP-SERVER 로 넘기기만 했고, 재시작해도 잃을 것이 없었습니다.
지금은 `pos_server` 데이터베이스와 **아홉 개의 표**를 갖고 있습니다.

| 문서 | 무엇 | 표 |
| --- | --- | --- |
| §3.1~3.2 | TR 매출 수신·분해 | `tr_sale_log`, `tr_sale_header/detail/payment/etc` |
| §3.3 | ETC 매출 수신 (분해는 없음) | `etc_sale_log` |
| §3.4 | 개점·마감 IRT | `pos_business_state`, `pos_business_hist` |
| §3.5 | Live Check · 시각 동기화 | `pos_live_report` |
| §3.5 | 프로그램 배포 | `pos_program_release`, `pos_program_install` |
| §3.5 | 공지·긴급 메시지 | `pos_notice`, `pos_notice_receipt` |
| §3.6 | 마스터 IRT 배포 | `pos_master_version`, `pos_master_dispatch` |

주소는 `Debian-Setting` 의 `docs/docker.md` 에 표로 있습니다. 설계 이유는
umbrella `docs/adr/0013`.

### 주문 하나에 메뉴 여럿 (§4.4.2)

어제까지 주문 하나는 메뉴 하나였습니다. 손님 화면의 장바구니부터
`order_line` 표까지 한 줄로 이어졌습니다:

```
장바구니(채널) → APP 원장 app_order_detail → OMS(Order) lines → order_line 표
                                                      ↓
                                     POS 카드·영수증 / KDS 티켓 / BO 매출 조회
```

`menuName` 과 `amount` 의 **뜻이 바뀌었습니다** — 이제 메뉴 이름이 아니라
주문의 이름("짜장면 외 1건")이고 줄들의 합입니다. 자세한 것은 adr/0012 의
2026-09-18 추가분.

### 매장에서 쓰는 방식 셋 (Sun&Moon의 지적에서 나온 것)

- **강제 수령** — 번호를 못 대는 손님이 실제로 있습니다. 검사를 *선택*으로
  바꾸지 않고 **표시된 우회로**를 뒀습니다. `pickup_override` 로 남고 BO
  매출 조회에 배지로 뜹니다.
- **DID는 흐릅니다** — 조리 중 / 조리 완료 두 칸, `called_at` 기준 90초.
  안 가져갔다고 붙들고 있으면 화면이 목록이 되고, 목록에서는 방금 나온
  번호가 묻힙니다.
- **KDS 다시 부르기** — DID가 흐르니까 지나간 뒤에 온 손님은 다시 불러야
  합니다. 화면은 DID지만 손님이 왔는지 아는 사람은 주방에 있습니다.

### BO 화면 다섯 묶음

- 개점 현황 / Live Check / 배포 현황 / 단말 공지 — 전부 `/api/pos-ops/*` 로
  POS-Server 를 **읽기만** 합니다.
- 기준정보 공통 CRUD — `/master/:code` 하나가 회사·브랜드·거래처·카드사를
  전부 그립니다 (adr/0014).

## 2. 다음에 집을 것 — 순서대로

### 1순위. 재처리 (§5.8, §10)

**지금 실패는 기록만 되고 되돌릴 길이 없습니다.** 세 군데가 전부 그렇습니다:

- 매출 분해 실패 (`tr_sale_log.status = 'FAILED'`) — 실서버에 지금도
  거래 `000503` 하나가 FAILED 로 남아 있고, 영원히 그대로입니다.
- 마스터 적용 실패 (`pos_master_dispatch.status = 'FAILED'`)
- 프로그램 설치 실패 (`pos_program_install.status = 'FAILED'`)

셋 다 "다시 시도" 버튼 하나와 배치 하나면 됩니다. 그리고 adr/0014 의
마지막 표가 말하듯 **이것이야말로 공통화할 것**입니다 — 세 개를 따로
만들면 세 번째쯤에서 모양이 갈립니다.

어제 §3.1을 만들면서 제가 낸 구멍이라 제일 먼저 메우는 것이 맞습니다.

### 2순위. OMS §5.4 상태 변경 전달

POS-Server 가 개점·마감·재개점·Live 상태를 이제 정확히 압니다. 그걸
APP-SERVER 와 외부 채널로 흘려보내는 길이 **아직 없습니다** — 손님 앱은
매장이 마감했는지 여전히 모릅니다. 재료가 다 있어서 잇기만 하면 됩니다.

문서가 전달하라는 것: 매장 주문 가능 상태 / 결품과 해제 / POS 개점 /
POS 마감 / 같은 판매일자의 재개점 / POS Live.

### 3순위. 결제 (§4.10)

`app_order_payment` 는 표만 있고 행이 0입니다. 장바구니가 붙은 지금,
**플랫폼이 돈을 못 받는다**는 것이 가장 큰 기능 구멍입니다.

### 그 뒤

- ETC 매출 분해 (§3.3) — 문서가 상세 표 모양을 미뤄 뒀습니다.
- §5.8 나머지 배치 — POS 수신 확인 없는 주문, 장기 미처리, 중복, 정합성 비교.
- §4.1 인증 / §4.7 GIS — 손님이 지금 익명이고, 주소로 매장을 못 찾습니다.
- §6 BO의 나머지 — 카드 승인(APP), 구매·발주(BUY), 일마감·정산(CLS),
  가맹점 청구(FRC), 프로모션(PRM), 매출 분석(SAL), 카드 매입(TOT).

## 3. "모든 것을 공통으로" — 다음 주의 큰 주제

Sun&Moon: *"가능하면 모든것을 다 공통으로 해서 하는 작업을 다시 한번
총 정리 하고 싶어요."*

adr/0014 가 그 첫 번째 사례입니다. 이 플랫폼에서 **실제로 되풀이되는
것**은 다섯 가지이고, 비슷해 보이지만 아닌 것과 구별하는 것이 요령입니다.

| 되풀이되는 것 | 지금 상태 | 공통화하면 |
| --- | --- | --- |
| 기준정보 CRUD | **했음** (adr/0014) | 정의 한 줄 = 화면 하나 |
| 실패 재처리 | **없음** | 위 1순위. 세 군데가 같은 모양 |
| 업스트림 읽기 | `Http*Repository` 넷이 거의 같음 | 타임아웃·502 규칙을 한 곳에 |
| 배포와 적용 결과 | 마스터(§3.6)와 프로그램(§3.5)이 같은 모양 | "무엇을 누구에게 내리고 적용됐나" 하나로 |
| 원본 수신 + 나중 분해 | TR 매출. ETC가 같은 모양으로 올 예정 | 수신 로그 + 분해 배치 + 재처리 하나로 |

**공통화하면 안 되는 것**도 같이 적어 둡니다. 이 이틀 동안 계속 나온
판단이고, 다음에 다시 부딪힐 것들입니다:

- **무엇이 일어나는 화면.** 결품(눌러서 걸고 푸는 타일), Live Check
  (축을 나눠 보는 것이 존재 이유), 매출(접었다 펴는 것), DID(흐르는 것).
  격자로 만들면 전부 못 쓰게 됩니다.
- **상태 기계.** 주문 상태, 개점·마감, 배포 상태는 모양이 비슷하지만
  규칙이 다릅니다. 재개점은 서버가 판단하고, 수령은 문이 하나여야 하고,
  적용 버전은 장비가 말해야 올라갑니다. 하나로 묶으면 그 규칙들이 설정이
  되고, 설정이 되면 아무도 안 읽습니다.
- **업무 이름.** 같은 "개점"이 Order 에서는 매장이 주문을 받는가이고
  POS-Server 에서는 그 단말이 매출을 올릴 수 있는가입니다. 이름이 같다고
  합치면 POS 하나가 마감할 때 가게가 닫힙니다.

## 4. 알고 두는 것들 (다음에 물어볼 만한 것)

- **Quartz가 메모리 스케줄러입니다.** Device Server 가 내려가 있는 동안
  매출 분해가 멈춥니다. 미처리 원본은 남아서 유실은 없습니다.
- **임계값·알림이 아무 데도 없습니다.** Live Check 도, 재전송 목록도,
  강제 수령 건수도 전부 사람이 화면을 열어야 보입니다. Grafana 에 걸려면
  영업시간 필터가 먼저 필요합니다(밤에는 영업 축이 중단이라 전부 빨갛습니다).
- **Trace ID 가 없습니다** (§10). 서비스 여섯을 가로지르는 요청 하나를
  추적할 수 없습니다.
- **BO `devices` 가 `device_id` 단독 PK 입니다.** 단말은 (매장, 번호, 종류)
  인데 키가 안 맞고, 매장별 장비 인증의 전제입니다.
- **Live Check 의 데이터 축이 매장 단위입니다.** POS 단위로 좁히려면
  분해 실패를 POS번호로 세면 됩니다.
- **공통 CRUD 권한이 한 겹입니다.** 브랜드를 고치는 사람이 거래처도 고칩니다.
- **공통 CRUD 가 복합키를 못 다룹니다.** `common_codes` 가 그런 표입니다.

## 5. 돌려면 (다음 주 첫 5분)

```bash
ssh schware@192.168.0.2 '
docker ps --format "{{.Names}}\t{{.Status}}"
for u in http://localhost:8080/bo/actuator/health \
         http://localhost:8083/order/actuator/health \
         http://localhost:8085/channel-order/actuator/health \
         http://localhost:8086/app-server/actuator/health \
         http://localhost:8087/health ; do
  printf "%-52s " "$u"; curl -s -o /dev/null -w "%{http_code}\n" --max-time 8 "$u"
done'
```

화면:

- BO `http://192.168.0.2:8080/bo/`
- 손님 주문 `http://192.168.0.2:8085/channel-order/`
- POS / KDS / DID `http://192.168.0.2:8000/{pos,kds,did}/`
- Grafana `http://192.168.0.2:10000`

고치고 올리는 경로 세 가지는 `Debian-Setting` 의 `docs/development.md` §3.
