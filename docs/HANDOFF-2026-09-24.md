## 1. POS가 거래 원장을 갖습니다 (ADR-0010 1단계)

ADR-0010의 단계표에서 **1 — IndexedDB 큐 + 로컬 채번**이 들어갔습니다.
2단계(SQLite)는 그대로 남습니다.

**이건 기능이 아니라 조용한 사고를 고친 것입니다.** 거래번호가
`localStorage` 에 있었는데, 거기에는 번호와 거래를 함께 묶을 방법이
없습니다. 번호를 올린 직후 브라우저가 죽으면 번호가 되돌아가고, **같은
번호가 두 번** 올라가 서버의 유일 제약에 부딪혀 **손님 앞에서 수락이
실패**합니다.

이제 번호와 거래가 한 IndexedDB 트랜잭션에서 납니다.

```
수락  →  [번호 올림 + 거래 적음]  →  서버에 상태 변경  →  거래를 PENDING 으로
                 한 트랜잭션                                    ↓
                                                    30초마다 POST /sales (배열)
```

화면에 **미전송 건수**가 뜹니다. `EVENTS_REDIS` 때처럼 안 보이는 곳에서
차오르는 큐는 조용한 실패가 됩니다.

**마감이 전송을 검증합니다** — 올려 보고, 남으면 몇 건인지 말합니다.
막지는 않습니다(서버가 죽었는데 매장을 못 닫게 하면 더 나쁩니다).

> `POST /sales` 는 이미 배열을 받고 중복을 실패로 안 봤습니다. ADR-0010을
> 예상해서 만들어 둔 자리였고, 단말만 붙이면 됐습니다.

**남은 것**: 거래 전문의 `payments` 가 비어 있습니다. 결제는 APP-SERVER가
OMS 앞에서 승인하므로 **POS를 지나지 않습니다.** 승인번호가 거래까지
따라오게 하는 것은 따로 할 일입니다 — 지어 넣으면 POS가 보지 못한
사실이 매출에 남습니다.

## 2. 영수증이 교환권이 됩니다 (ADR-0007 주문 QR)

2026-09-16의 합의 순서 `A 테이블 → A' 결품 → B 수령 → C 영수증` 에서
**C**가 남아 있었습니다.

주문마다 128비트 난수를 갖고, 그 값이 영수증 QR에 실립니다. 손님이
찍으면 `/channel-order/o/{token}` 이 열립니다 — 로그인도 회원번호도
필요 없습니다. **설계서의 주문 상태 조회가 그동안 못 만들어진 이유가
"손님을 가리킬 방법이 없어서"였고, 종이가 그 자리를 채웁니다.**

돌려주는 것은 주문이 아니라 `ClaimView` 입니다. 인증 없는 경로라 담는
쪽으로 만들었습니다 — PIN·단말 이름·거래번호는 빠집니다.

QR은 **단말에서 그립니다**. 서버가 이미지로 내려주면 네트워크가 끊긴
매장에서 QR 없는 영수증이 나갑니다.

> ⚠️ **도메인 문제가 이제 진짜로 걸립니다.** 테이블 스티커는 회수해서
> 다시 붙일 수 있지만 **나간 영수증은 못 고칩니다.** QR 주소는
> `VITE_CLAIM_BASE` 로 빌드 때 정하고, 지금은 공인 IP 입니다.

## 3. 단말이 BO에 등록됐는지 봅니다 (ADR-0008)

`AcceptKnownFormatDirectory` 가 id의 **모양만** 보고 있었습니다. 형식만
맞으면 아무 단말이나 붙었고, 이 서버는 공인 IP로 열려 있습니다.

APP-SERVER가 BO 마스터를 읽는 방법 그대로입니다 — `pos_server` 에
`v_bo_devices` 뷰를 걸고 읽습니다. 세션도 공유 비밀도 필요 없습니다.

`DeviceDirectory` 가 **(매장, 번호, 종류)**를 받습니다. 단말의 신원이
원래 그것인데 확인하는 자리만 그걸 몰랐습니다.

**기본값은 꺼짐입니다.** 켜려면 SQL을 먼저 돌려야 하고, 그건 superuser가
필요합니다:

```bash
ssh -t schware@192.168.0.2 'cd ~/apps/docker/db && sudo -u postgres psql -v ON_ERROR_STOP=1 -f pos-server-fdw.sql'
```

그다음 Device Server를 `-e DEVICE_DIRECTORY=bo` 로 다시 띄웁니다.

> **왜 켜는 것이 기본이 아닌가**: 뷰가 없는 서버에서 "막기"를 기본으로
> 두면 전 매장 단말이 조용히 못 붙고, 증상은 "등록되지 않은 단말"로
> 보여서 원인을 BO 장비 화면에서 찾게 됩니다. 그래서 명단을 한 번도
> 못 읽었을 때는 **막지 않고 크게 경고만** 합니다.

## 4. 회원번호 (§4.1)

손님이 익명이었습니다 — 주문마다 `guest-xxxxxx` 를 지어 붙여서, 같은
손님이 두 번 시켜도 다른 사람이었습니다.

2026-09-10에 정한 모양 그대로: **날짜(6) + 그날 순번(4) + 검증숫자(1)**.

**자리가 바뀌었습니다.** 그때는 "주문 채널에 자체 DB를 준다"였는데,
그때는 APP-SERVER가 없었습니다. 지금은 원장을 가진 쪽이 손님도 셉니다 —
새 데이터베이스를 안 만들어도 되는 것은 덤입니다(`createdb` 는 superuser).

검증숫자는 Luhn입니다. **한 자리 오타와 이웃 자리 바꿔치기**를 잡습니다.
지어낸 번호는 못 잡으므로 발급된 번호를 표에 적습니다.

**번호는 자격이 아니라 편의입니다** — 모르는 번호면 막지 않고 익명으로
처리합니다.

## 다음에 집을 것

HANDOFF-2026-09-18의 목록이 그대로 살아 있고, 여기에 이번 것들이
남긴 자리가 붙습니다.

### 이번 작업이 남긴 것

- **거래 전문의 결제 내역이 빕니다** (위 §1). 승인번호가 APP-SERVER에서
  거래까지 따라와야 합니다.
- **POS 로컬 DB 2단계 (SQLite / PWA)**. IndexedDB는 지워질 수 있습니다.
- **회원번호로 자기 주문 목록 보기**. 표와 인덱스는 준비됐습니다.
- **KDS가 주문 QR로 무엇을 하는가**. 아직 영수증에만 찍힙니다.
- **BO `devices` PK** — 여전히 `device_id` 단독이라 두 매장이 둘 다
  `01` 번 POS를 가질 수 없습니다. 지금 명단 대조는 이름이 전역에서
  유일하다는 전제 위에 있습니다.
- **도메인**. 영수증이 나가기 시작하면 IP 변경이 되돌릴 수 없어집니다.

### ETC 매출 분해 (§3.3) — **뼈대만 올라가 있습니다 (2026-09-25)**

> **→ 2026-09-27 에 배선 완료, 실서버 확인까지 했습니다.** 아래 다섯
> 단계 전부 했고, TR 회귀도 확인했습니다.
> [`HANDOFF-2026-09-27.md`](HANDOFF-2026-09-27.md) §4.

> ⚠️ **Device Server `ebaadc3` 의 코드는 실행되지 않습니다.** Bootstrap
> 에 연결하지 않았습니다. 컴파일되고 시험도 통과하지만 아무도 부르지
> 않는 상태이고, 그래서 지금 동작은 하나도 안 바뀌었습니다.

**만든 것** — TR(§3.1~3.2)과 ETC(§3.3)가 같은 모양이라 **원본
수명주기를 공통으로** 뺐습니다:

| | |
|---|---|
| `domain/intake/` | `RawLog` · `RawLogStore` · `IntakeJob` · `IntakeHandler` |
| `infrastructure/intake/JdbcRawLogStore` | 구현 하나. 표 이름과 키 컬럼만 다르게 주어 두 벌로 |
| `domain/etc/` + `infrastructure/etc/` | ETC 쪽의 "분해가 무엇인가" |
| `domain/reprocess/RawLogReprocessor` | `SaleReprocessor` 와 ETC 용이 같아서 합침 |
| `V5__etc_sale_decompose.sql` | `etc_sale_log` 에 `attempts`/`decomposed_at`, `etc_sale_detail` 신설 |

**선을 어디에 그었나**: 분해 결과를 어디에 넣는지는 **공통에 없습니다.**
TR 은 표 넷, ETC 는 하나로 갑니다. 그 차이를 공통에 끌고 들어오면
"공통" 안에 종류별 분기가 쌓입니다. 결과 저장과 `DECOMPOSED` 표시는
`IntakeHandler` 가 **한 트랜잭션으로** 가져갑니다.

마스터·프로그램 재처리는 **합치지 않았습니다** — 모양은 비슷해도
"다시 한다"의 뜻이 다릅니다(장비가 가져갑니다). 합치면 그 차이가
설정이 됩니다.

**남은 일 — 이어서 할 순서:**

1. **`JdbcSaleRepository` 가 수명주기를 `JdbcRawLogStore` 에 위임**하게
   합니다. 지금은 TR 이 자기 SQL 을 그대로 들고 있어서, 공통이 실제로
   공통이 아닙니다. **다시 쓰지 말고 위임만** 하십시오 — 살아 있는
   매출 경로라 동작이 바뀌면 안 됩니다.
2. **Bootstrap 배선**: `IntakeJob` 둘(TR·ETC)을 Quartz 에 걸고,
   `SaleReprocessor` 를 `RawLogReprocessor` 둘로 바꿉니다.
3. **`POST /etc-sales`** — `SaleEndpoints.receive()` 와 같은 모양.
   배열을 받고 중복을 실패로 보지 않습니다.
4. **`GET /etc-sales/totals`** — 정합성 확인용.
5. **시험** — 특히 `JsonEtcDecomposer` 의 평탄화(중첩·배열·깊이 제한)와
   `IntakeJob` 의 catch 둘(원본이 잘못된 것 vs 저장이 안 되는 것).

> **V5 는 다음 배포 때 실제로 돕니다.** 코드가 안 쓰더라도 적용되며,
> 컬럼과 표를 더하기만 하므로 기존 동작에는 영향이 없습니다.

### 그대로 남아 있는 것

- **결제수단 기준정보** — 공통 CRUD로 붙일 자리.
