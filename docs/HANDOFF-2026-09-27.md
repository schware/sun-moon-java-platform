## 1. 재부팅에서 11개 중 5개가 안 살아났습니다

서버가 2026-09-07 이후 20일 동안 재부팅된 적이 없었습니다. Sun&Moon이
직접 재부팅했고, **`--restart unless-stopped` 인데도 5개가 자동으로 안
떴습니다**:

| 살아남 (6) | 안 살아남 (5) |
|---|---|
| channel-order · device · kds · grafana · prometheus · node-exporter | **order · app-server · bo · delivery · landing** |

안 뜬 쪽은 `Exited (255)`, `RestartCount=0`, `StartedAt` 이 재부팅 **전**
날짜였습니다 — 재부팅 뒤에 **한 번도 시작을 시도하지 않은** 것입니다.
`docker start` 로 살렸고(저장된 env 그대로), 주문·BO·랜딩이 그 사이
몇 분 내려가 있었습니다.

**원인은 미확정입니다.** 데몬 로그가 필요한데 root 권한이 있어야
합니다. 확인 명령과 재부팅 뒤 점검 절차를 `Debian-Setting/docs/docker.md`
"재부팅 시 자동 시작" 에 적었습니다.

> **재부팅을 한 달에 한 번도 안 하는 서버라 이게 더 위험합니다.** 할
> 때쯤이면 이걸 기억하는 사람이 없습니다. 재현되면 `@reboot` cron 으로
> exited 컨테이너를 `docker start` 하는 한 줄을 검토할 것입니다.

그리고 이 재부팅으로 **제가 쓴 문장 둘이 틀렸다는 것**이 드러났습니다:

- 2026-09-25 "재부팅하면 `DEVICE_DIRECTORY` 가 꺼진다" — 틀림. 재부팅은
  env 를 안 바꿉니다. 빠지는 경로는 `stop-all`(rm 까지) → `start-all` 입니다.
- 2026-09-27 오전 "재부팅 자체는 위험하지 않다" — 틀림. env 는 안 바꾸지만
  **컨테이너를 안 살릴 수는** 있습니다.

둘 다 문서에서 고쳤습니다.

## 3. BO — 열흘째 새로고침에서 죽던 다섯 화면

**제일 오래 방치된 것이라 먼저 적습니다.** POS 운영 네 화면
(`/pos-business` · `/pos-live` · `/pos-deploy` · `/pos-notices`)과 기준정보
(`/master/:code`)가 2026-09-17~18 에 생긴 뒤로 **새로고침하면 401** 이었습니다.
눌러서 들어가면 멀쩡해서 아무도 몰랐습니다. 2026-09-10 에 `/menus` ·
`/stores` 가 닷새 동안 같은 이유로 죽었던 것과 똑같습니다.

원인은 **목록이 세 벌**이었던 것입니다 — 화면의 `App.tsx`, 서버의
`WebConfig`, `SecurityConfig`. 줄만 더하면 세 번째가 납니다. 그래서:

- 서버 쪽 둘이 `SpaRoutes` 한 목록을 봅니다.
- **`SpaRoutesTest` 가 `App.tsx` 를 읽어 서버 목록과 대조합니다.** Java 에서
  TypeScript 를 읽는 게 어색하지만, 어긋나는 두 곳이 바로 그 두 언어라
  여기 말고는 둘을 한 번에 볼 곳이 없습니다. `/pos-live` 를 일부러 빼서
  시험이 그 이름을 대며 깨지는 것까지 확인했습니다.

### 재처리 화면

## 4. ETC 매출 분해가 실제로 돕니다 (§3.3)

2026-09-25 의 뼈대(`ebaadc3`)를 배선했습니다(`664a0f7`). HANDOFF-2026-09-24
에 적은 다섯 단계 그대로입니다.

**TR 이 공통 수명주기에 위임합니다.** 살아 있는 매출 경로라 다시 쓰지
않고 위임만 했고, 옮기기 전에 SQL 을 글자 단위로 대조했습니다. 한
군데(실패 목록의 `LIMIT 200`)가 달라서 공통 쪽을 TR 에 맞췄습니다.

`SaleDecomposeJob` · `SaleReprocessor` 는 지웠습니다 — 남겨 두면 공통화가
아니라 두 벌입니다.

### 실서버 확인

| | 결과 |
|---|---|
| **TR 회귀** — 실패한 `000503` | 배포 전후 `FAILED attempts=397` 그대로. **배치가 다시 안 집어 갔습니다** — 388번 사고의 교훈이 위임을 거쳐서도 살아 있습니다 |
| TR 정상 / 금액 틀림 | DECOMPOSED 상세 2줄 / FAILED + 사유 |
| ETC 정상 | DECOMPOSED, 상세 10줄 — `coupon.code`, `items[0].name`, `memo = <null>` |
| ETC 중복 | `duplicates: 1` (실패 아님) |
| ETC 너무 깊음 / 키 없음 | FAILED + 사유 / 400 |
| 재처리 | 네 종류가 한 목록. ETC 되돌리기 → RECEIVED → 다시 FAILED `attempts=2` |

시험에 쓴 `pos-intake` 줄은 지웠습니다(새 재처리 화면에 가짜 할 일로
남으면 안 되니까).

### 이 공통화에서 선을 그은 자리

- **분해 결과를 어디에 넣는지는 공통에 없습니다.** TR 은 표 넷, ETC 는
  하나. 그 차이를 공통에 끌고 들어오면 "공통" 안에 종류별 분기가 쌓입니다.
- **마스터·프로그램 재처리는 합치지 않았습니다.** 모양은 비슷해도 "다시
  한다" 의 뜻이 다릅니다(장비가 가져갑니다).
- **ETC 상세는 이름·값입니다.** §3.3 이 구조를 미뤘습니다. 구조가 정해지는
  날 할 일은 새 표를 만들고 **원본을 다시 분해하는** 것입니다 — 원본을
  바이트로 들고 있는 것이 그때 값을 합니다.
