## 0. 오늘 정한 것 (09-29)

- **단말 첫 화면은 매장·장비 입력** — 페어링 화면을 뺐습니다(POS `173a41f`, KDS `a30b086`, DID `8a2e3cc`, 배포됨).
  - 같은 날 저녁: 새벽에 브라우저로 페어링해 둔 기록(`store-01/pos-01`)이 남아 있어 같은 주소(`:8000`)의
    KDS·DID 가 입력 화면을 건너뛰고 `pos-01` 로 열렸습니다. **브라우저에서는 저장된 페어링을 보지 않고
    지우도록** 고쳤습니다(POS `54eafaf`, KDS `bbed545`, DID `19739aa`, 배포됨). 서버에 남은 그 자격 1건은 해제했습니다.
- **페어링은 Sun&Moon 이 다시 설계합니다.** 그때까지 페어링 코드는 손대지 않습니다 — 아래 §5 에 위치만.
- 앞으로는 결정을 Sun&Moon 이 하고, 새 개념은 먼저 여쭙고 만듭니다.

## 0-1. 10-01 에 정한 것

- **토큰은 제외합니다.** API 통신 토큰이어야 하는데, 결국 장비에 대한 토큰이 될 수밖에 없어서입니다.
- **KDS·DID 의 짝은 STORE-ID 입니다.** 같은 매장의 KDS 와 DID 가 함께 움직이고, 따로 묶는 설정은 없습니다.
  DID 는 이미 그렇게 동작합니다(같은 매장의 조리 중·완료 목록, 다시 부르기 시각 `calledAt`).
- 그래서 페어링(BO 코드 → 기기 토큰)을 **걷어냈습니다**(§5). 셸도 웹 단말처럼 첫 실행 때 매장·장비를 넣습니다. (commit·배포 전)
- **KDS MAIN / SUB 는 유지 — BO 가 정합니다.** BO 장비의 KDS 역할(예: `kds-01` MAIN, `kds-02` SUB)을 Device
  Server 가 읽어 KDS 화면이 따르고, 메인의 일은 서버가 다시 확인하며, MAIN 이 3분 넘게 끊기면 생산 KDS 가
  비상 수령합니다. (commit·배포 전. 서버 DB 의 `v_bo_devices` 에 `kds_role` 칸은 더해 둠)
- 단말 등록의 기본값을 화면마다 따로 기억합니다(POS `cc25353`, KDS `7172c58`, DID `7e35a6b`, 배포됨).
