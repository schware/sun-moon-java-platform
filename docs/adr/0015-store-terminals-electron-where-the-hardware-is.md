# ADR-0015: 매장 단말은 하드웨어가 있는 곳만 Electron — KDS-MAIN이 주방의 중심

- **Status**: Accepted (방향 결정, 구현 전)
- **Date**: 2026-09-27
- **Deciders**: Project owner

## Context

지금 매장 단말(POS · KDS · DID)은 전부 **서버가 내려주는 웹 화면**입니다.
nginx 가 정적 파일을 주고, 브라우저 탭이 단말입니다. 그동안 그 방식에서
막힌 곳이 쌓였습니다:

- **POS 원장이 지워질 수 있습니다.** ADR-0010 1단계로 IndexedDB 에 원장을
  두었지만, 브라우저 데이터 삭제 한 번이면 올리지 못한 거래가 사라집니다.
- **영수증 프린터·돈통·VAN 카드 단말**은 브라우저가 붙잡을 수 없습니다.
- **서버가 안 보이면 POS 화면 자체가 안 뜹니다** — 화면 파일이 서버에 있어서.
- **라벨 재출력**이 필요합니다. 라벨이 걸리거나 잘못 붙으면 그걸 아는 사람은
  주방에 있고, 재출력 버튼은 KDS 에 있어야 합니다.

그리고 매장 배치에 대한 사실 하나가 결정을 정했습니다:

> **POS 와 KDS 의 위치는 엄청 멀어요. 그 위치 때문에 KDS 중심의 주방이
> 되어야 해요.**

네트워크 프린터라면 같은 LAN 안에서 POS 가 대신 보낼 수는 있습니다. 하지만
그러면 **주방이 카운터 PC 에 매달립니다** — POS 가 꺼지거나 바쁘면 주방이
라벨을 못 뽑고, 문제가 생기면 멀리 떨어진 두 곳을 오가며 찾아야 합니다.
**주방은 주방에서 끝나야 합니다.**

## Decision

### 하드웨어가 있는 단말만 Electron

| 단말 | 형태 | 이유 |
|---|---|---|
| **POS** | Electron | 원장(SQLite), VAN, 영수증 프린터·돈통, 서버 없이도 화면이 뜸 |
| **KIOSK** | Electron | VAN, 영수증 프린터, 무인 운영(종료 불가·자동 재시작) |
| **KDS-MAIN** | Electron | **주방의 중심** — 라벨 프린터, KDS SUB 와 DID 관리 |
| **KDS SUB** (생산 KDS) | 웹 — 지금 방식 그대로 | 화면뿐입니다. 만들 메뉴를 보고 끝냅니다 |
| **DID** | 웹 | 표시뿐입니다 |
| APP / QR 테이블 | 웹 | 손님 휴대폰에 앱을 깔게 할 수 없습니다 |

**KDS 는 "무엇을 만들어야 하나" 를 보는 화면입니다.** 하드웨어를 붙잡는
것은 KDS-MAIN 하나로 모읍니다. 생산 KDS 가 하드웨어를 관리하기 시작하면
주방 화면이 매장 장비 관리자가 됩니다.

코드 이름과의 대응: 9/18 에 만든 `KdsRole` 의 `PRODUCTION` 이 이 ADR 의
**KDS SUB** 이고, `MAIN` 이 **KDS-MAIN** 입니다.

### KDS-MAIN 은 관리하되, 점서버가 아닙니다

KDS SUB 와 DID 는 **지금처럼 중앙 서버에 붙습니다.** KDS-MAIN 은 서버를 통해
**명령**합니다:

```
KDS-MAIN → 서버 → KDS SUB / DID
```

9/17 의 **"다시 부르기"** 가 이미 이 모양입니다 — KDS 는 DID 를 직접 조종하지
않고, 서버에 `called_at` 을 남기면 DID 가 그걸 보고 다시 띄웁니다.

**붙는 곳과 명령하는 쪽은 다릅니다** (Sun&Moon, 2026-09-27). KDS SUB 와 DID 는
중앙 서버에 붙어 있지만, **주방 쪽 단말에 명령을 내리는 주인은 KDS-MAIN
하나**입니다. 서버는 전달할 뿐이고, 다른 단말이 KDS SUB 나 DID 에 명령하는
길은 두지 않습니다. 명령의 주인이 여럿이면 누가 무엇을 바꿨는지 되짚을 수
없습니다. (다시 부르기는 9/18 KDS 분리 때 이미 MAIN 에만 있습니다.)

명령에는 두 층이 있고, 섞지 않습니다:

| 층 | 누가 | 무엇 |
|---|---|---|
| **매장 운영** | **KDS-MAIN** | 다시 부르기, DID 표시·새로고침, KDS SUB 관리, 라벨 재출력 |
| **본사** | BO | 공지·긴급 메시지, 프로그램 배포, 마스터 배포 |

BO 는 모든 단말에 공지를 걸 수 있지만, 그건 "이 주문을 다시 불러라" 같은
매장 운영 명령이 아닙니다. 주방의 흐름은 주방에서 정합니다.

**반대 모양(KDS SUB·DID 가 매장 LAN 에서 KDS-MAIN 에 직접 붙는 것)은
택하지 않습니다.** 그러면 KDS-MAIN 이 점서버가 됩니다 — ADR-0010 이 "매장
LAN 에서 단말끼리 직접 잇는 것은 점서버를 작게 다시 만드는 것" 이라고 적은
그 모양입니다. KDS-MAIN 이 꺼지면 나머지가 같이 꺼지고, 얻는 것도 없습니다
(주문은 어차피 중앙을 거쳐 오므로 중앙이 죽으면 앱이어도 티켓이 없습니다).

### 매장을 통제하는 흐름 — 상태마다 주인이 하나 (Sun&Moon, 2026-09-27)

```
POS / KIOSK       주문을 받아서 결제하는 곳
OMS → POS         외부·APP 주문을 매장에서 처리하는 곳
POS / KIOSK → KDS-MAIN     주문의 처리 — 주방의 중심
KDS-MAIN → KDS SUB, DID    주방이 처리한 결과를 보여주는 화면들
```

Sun&Moon 의 말: *"조리 완료 상태, 픽업 등 다양한 상태를 전달할 때 중심점이
생긴다."* 그게 이 구조의 값어치입니다 — **상태마다 정하는 주인이 하나**가
됩니다.

화살표는 **결정이 넘어가는 방향**이지 **누가 누구에게 직접 붙는가**가
아닙니다. 모든 단말은 여전히 중앙에 붙고(점서버 없음), 사실이 적히는 곳은
여전히 OMS 입니다. KDS-MAIN 은 주방의 결정권자이지 주방 상태의 저장소가
아닙니다.

| 상태 | 주인 | 지금 코드 (2026-09-27) |
|---|---|---|
| 주문 접수 | 채널(APP·QR·외부·KIOSK·POS) → OMS 기록 | ✅ |
| 수락 / 거절 | POS | ✅ — KIOSK 주문의 수락은 미정 |
| 조리 시작 (내 줄) | KDS SUB | ⚠️ SUB 가 **주문 전체**를 COOKING 으로 바꿉니다 |
| 조리 완료 (내 줄) | KDS SUB | ✅ 줄 단위 (9/18) |
| 주문 전체 조리 완료 | 자동 — 모든 줄이 끝나면 | ✅ |
| 강제 전부 완료 | KDS-MAIN | ⚠️ 아래 참고 |
| 호출 (DID) | 첫 호출 자동, 다시 부르기 KDS-MAIN | ⚠️ 화면에서만 MAIN |
| 픽업 (수령) | KDS-MAIN | ⚠️ 화면에서만 MAIN |
| 라벨 출력·재출력 | KDS-MAIN | 새로 |

### ⚠️ 지금 서버는 KDS-MAIN 을 모릅니다

**MAIN 은 화면의 `sessionStorage` 값일 뿐입니다.** 단말 등록 때 고르고 그
창이 기억합니다. 서버(Device Server, Order)에는 "이 기기가 MAIN 인가" 라는
개념이 없습니다. 그래서:

- **수령과 다시 부르기가 "MAIN 에만 있다" 는 것은 화면에서 버튼을 숨긴
  것뿐입니다.** 서버는 어느 KDS 의 요청이든 받습니다.
- **MAIN 의 "전부 조리완료" 버튼은 이름대로 동작하지 않습니다** (코드를
  읽은 결과, 실서버로는 아직 확인 안 함). 서버는 누른 기기에 **배정된 줄만**
  끝냅니다(`OrderLine.belongsTo`). MAIN 에는 배정된 줄이 없으므로, 줄이 전부
  SUB 에 배정돼 있으면 MAIN 이 눌러도 아무 줄도 안 끝납니다.
- **COOKING 은 SUB 한 대가 주문 전체를 움직입니다.** SUB 가 남의 줄까지
  말하는 모양이고, HANDOFF-2026-09-18 §4 에 이미 적어 둔 구멍입니다.

**중심점을 실제로 만들려면 서버가 역할을 알아야 합니다:**

1. BO 장비 마스터에 KDS 역할(MAIN / SUB) — 사람이 정하는 기준정보.
2. 기기 인증(키·페어링) 때 역할이 확정되고, 단말이 스스로 고르지 않습니다.
   위 열린 질문 1(웹에서 MAIN 막기)과 2(매장당 하나)가 여기서 같이 풀립니다.
3. 명령마다 서버가 확인합니다 — 수령·다시 부르기·강제 완료·라벨은 MAIN 만.
4. SUB 는 자기 줄만 말합니다. 주문의 "조리 중" 은 "한 줄이라도 시작됨" 으로
   서버가 계산합니다 — 조리 완료를 계산하는 방식과 같습니다.
5. MAIN 의 강제 완료는 **표시된 우회로**로 — 강제 수령(9/17)처럼 누가 강제로
   끝냈는지 남깁니다. SUB 화면이 고장 나도 주방이 멈추지 않게 하는 길이지만,
   SUB 가 끝낸 것과 구분돼야 합니다.

### 라벨 출력 — 실행은 주방에서, 기록은 서버에

```
KDS-MAIN "라벨 다시" → 서버에 출력 작업 기록 → KDS-MAIN 이 옆 프린터로 출력 → "찍었다" 보고
```

기록을 서버에 남기는 이유:

1. **재출력은 같은 것을 다시 찍는 것입니다.** 그때 데이터로 다시 그리면,
   그 사이 메뉴 이름이 바뀌었을 때 처음 라벨과 재출력 라벨이 달라집니다.
   처음 찍은 내용을 남겨 두고 그대로 다시 보냅니다.
2. **보낸 것과 찍힌 것은 다릅니다** (§3.6 마스터 배포와 같은 규칙). 실행자가
   "찍었다" 고 말해야 찍힌 것입니다.
3. **재출력 횟수가 의미 있습니다.** 라벨은 보통 포장 하나에 하나라, 겹치면
   같은 라벨이 두 장 돌아다닙니다. 라벨에 "재출력 N" 을 찍습니다.
4. **실패는 재처리 화면으로 갑니다** — 다섯 번째 종류.

### Electron 은 앱 셋이 아니라 셸 하나

POS · KIOSK · KDS-MAIN 을 **하나의 셸 + 역할**로 만듭니다. 설치 파일 하나,
설치할 때 역할을 정합니다. 역할마다 열어 주는 하드웨어가 다릅니다:

| 역할 | 열어 주는 기능 |
|---|---|
| POS | 원장, VAN, 영수증 프린터, 돈통 |
| KIOSK | VAN, 영수증 프린터, 화면 잠금 |
| KDS-MAIN | 라벨 프린터 |

셸 하나인 이유: 보안 설정(화면에서 Node 를 못 쓰게, 필요한 기능만 좁은
창구로)을 한 곳에서 지키고, 코드 서명이 하나이고, 지금 단말 셋이 같은
코드를 복사해 들고 있는 문제(`useTerminalSocket.ts` 100줄이 셋 다 똑같음)를
세 벌로 키우지 않기 위해서입니다.

**업데이트는 두 층입니다.** 셸(드묾, 무겁고 서명 필요)과 화면 번들(잦음,
가벼움)을 가르고, 화면 번들은 §3.5 프로그램 배포로 내립니다. 그래야 지금
`tar` 로 올리면 바로 바뀌는 속도를 잃지 않습니다.

### 기기 인증

- Electron 단말(POS · KIOSK · KDS-MAIN) — 설치할 때 기기 키를 심습니다.
- 웹 단말(KDS SUB · DID) — **페어링 토큰**: BO 가 일회용 코드를 발급하고,
  단말이 한 번 입력하면 서버가 기기 전용 토큰을 줍니다.

둘 다 지금의 "그 이름이 명단에 있나"(ADR-0008 추가분)보다 강합니다.

## Consequences

- **ADR-0010 의 두 줄을 고칩니다.** "2단계는 PWA 를 먼저" → POS 는 Electron
  (SQLite). "KDS 와 DID 는 무상태로 남는다" → KDS SUB 와 DID 는 그대로이고,
  **KDS-MAIN 은 라벨 출력 기록을 갖습니다.** "점서버 없음" 은 그대로입니다.
- **서버 쪽은 거의 안 바뀝니다.** 단말이 말하는 방식(WebSocket + REST)이
  같습니다. 새로 생기는 것은 출력 작업 표, KDS-MAIN 의 관리 명령, 페어링.
- **§3.5 프로그램 배포의 첫 실제 대상이 생깁니다.** 9/17 에 만들 때는 배포할
  프로그램이 없었습니다. `device_type` · 매장별 우선 · 설치 상태가 이미 있습니다.
- **설치와 업데이트라는 새 일이 생깁니다.** 처음 한 번은 매장에 가서 깔아야
  하고, 코드 서명 인증서는 연간 비용이 듭니다. Electron 안의 Chromium 보안
  패치를 따라가는 것도 우리 일이 됩니다.
- **실물 장비 없이는 검증이 안 됩니다** — 프린터, VAN 단말.

## 열린 질문

> **2026-09-28: 아래 일곱 개 모두 [`design/store-app.md`](../design/store-app.md)
> §0 에서 기본값으로 정했습니다.** 요약: 1 막음(역할은 BO 가 정하고 페어링 때
> 따라옴) · 2 서버가 두 번째 MAIN 거절 · 3 MAIN 이 3분 끊기면 SUB 에 비상 수령 ·
> 4 1단계는 다시 부르기·연결 상태·새로고침 · 5 조리 완료 시, 줄 단위, 수량만큼,
> 재출력은 MAIN 만, 네트워크 프린터 · 6 Windows PC · 7 인터페이스만, 그 전까지
> 썬앤문페이. 바꾸려면 설계 문서의 `▶ 기본값` 자리를 고치십시오.

1. **웹 KDS 에서 MAIN 을 고를 수 있게 둘 것인가.** MAIN 이 Electron 으로 가면,
   브라우저로 MAIN 을 여는 순간 라벨 프린터 없는 허브가 하나 더 생깁니다.
   웹에서는 MAIN 을 막거나 보기만 되게 하는 쪽이 맞아 보입니다.
2. **매장당 KDS-MAIN 은 하나.** 둘이면 DID 명령이 겹칩니다. Device Server 가
   두 번째를 막아야 합니다.
3. **KDS-MAIN 이 꺼지면.** KDS SUB 는 계속 만들고 DID 도 계속 보여줍니다.
   멈추는 것은 **라벨 출력과 수령 처리**입니다 — 9/18 에 "수령 확인" 을 MAIN
   에만 두었기 때문에, MAIN 이 꺼지면 다 만든 주문이 `PRODUCED` 에서 넘어가지
   못합니다. Electron 자동 재시작으로 대부분 막히지만, **비상시 SUB 에서 수령을
   대신할 길**을 둘지 정해야 합니다.
4. **"DID 관리" 의 범위** — 다시 부르기 외에: 켜져 있나 보기, 새로고침, 어느
   매장·층을 보여줄지.
5. **라벨** — 처음 출력 시점(수락 / 조리 완료), 단위(주문 / 줄 / 수량 하나마다),
   재출력 권한, 라벨 내용, 프린터 연결(KDS-MAIN PC 에 USB / 네트워크).
6. **매장 장비** — Electron 단말은 Windows·macOS·Linux PC 에서만 돕니다.
   KDS SUB 와 DID 는 웹이라 태블릿·TV 스틱도 됩니다.
7. **VAN 사** — SDK 가 Windows DLL 이면 POS·KIOSK 는 Windows 로 고정됩니다.
